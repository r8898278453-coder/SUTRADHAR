# Sutradhar System — Complete Architecture Blueprint (v6.0 Production)

## 1. Core Design Philosophy

Do alag layers, do alag zimmedariyan:

| Layer | Kaam | Technology |
|---|---|---|
| **Communication Layer** | Insaan ko dikhane ke liye, alerts, manual override | Telegram (Bots + Group) |
| **Shared State Layer (Brain)** | System ki "truth" — kaun master hai, konsa ticket kis stage me hai, konsa project pe kaam hua | Central Shared Database (Firestore / Atomic CAS Engine) |
| **Intelligence Layer** | Asli "sochna, samajhna, code likhna, decide karna" | LLM Agent (Gemini Pro / Claude) + role-specific System Prompt |
| **Execution Layer** | Actual kaam — git, testing, AI Studio automation | Har Sutradhar ka local system (Docker Container Isolation) |
| **Oversight Layer** | Human control — pause, resume, force override | Telegram commands + Live Dashboard |

**Golden Rule:** Telegram sirf *bolta* hai kya hua. Shared Database *yaad rakhta* hai kya hua. Koi bhi bot decision Telegram message padh ke nahi, Database padh ke lega.

---

## 2. Shared State Layer — "The Brain"

### Kya use karein?
Recommend: **Firestore (ya koi bhi NoSQL/SQL DB jo atomic transactions support kare)** — Firebase Firestore, Supabase, ya self-hosted Postgres/SQLite+API. Reason:
- **Atomic transactions** — 2 bots ek saath likhne ki koshish karein to DB khud guarantee deta hai sirf ek jeetega (compare-and-swap). Ye Telegram pinned-message se zyada reliable hai.
- Har system (chahe kahin bhi ho) internet se seedha connect kar sakta hai — koi central server manage nahi karna padta (agar Firestore jaisi managed service lein)
- Free tier kaafi hai is scale ke liye

### Data Model (Collections/Tables)

```
📁 system_state
   └── current_master: { worker_id, since_timestamp, last_heartbeat, epoch }
   └── global_status: "RUNNING" | "PAUSED" | "MAINTENANCE"
   └── max_concurrent_workers: 6

📁 workers
   └── worker_id: { role, status (idle/busy/offline), current_ticket, 
                     last_seen, machine_info, capabilities, quota_usage, github_identity }

📁 projects
   └── project_id: { name, git_repo_url, priority, status, 
                       created_at, config_hash }

📁 tickets
   └── ticket_id: { project_id, title, description, scope 
                     (exact file paths/APIs allowed), status 
                     (open/claimed/in_progress/review/done/failed/blocked_clarification/needs_human_review), 
                     claimed_by, claimed_at, attempt_count, max_attempts,
                     branch_name, depends_on, clarification_question, rollback_commit }

📁 audit_log
   └── log_id: { timestamp, actor, action, ticket_id, reasoning, details }

📁 config
   └── shared environment config, dependency versions, secrets refs, prompt_templates (v1, v2)
```

Ye poora structure **single source of truth** hai. Koi bhi naya worker join ho, sirf isi DB ko padh ke turant context samajh jayega — "master kaun hai, kaunse projects hain, kaunse tickets open hain, kya pehle kaam ho chuka hai" — bina Telegram history scroll kiye.

## 3. Intelligence Layer — Skill Kahan Se Aati Hai

**Zaroori samajhna:** Sutradhar bot khud "smart" nahi hai. Bot ek **wrapper/orchestrator script** hai jo har decision-point pe ek **LLM (jaise Gemini Pro)** ko call karta hai, use poora context deta hai (DB se: ticket details, project conventions, related code/tickets), aur LLM ka jawab (code, decision, git command, question) leke aage execute karta hai. Poori "full-stack dev skill", "git troubleshooting", "web reading/understanding" — ye sab LLM ki apni capability se aati hai, bot script se nahi. Bot sirf plumbing hai.

### 3.1 Har Role Ka Apna System Prompt

**Master ka System Prompt** encode karega:
- Full-stack architecture reasoning — feature ko independent, non-overlapping tickets me todna (frontend / backend / DB migration / API contract / tests), dependencies samajhna
- Ticket likhne ka format — exact scope, exact file paths/APIs, clear "definition of done"
- **Assumption na banane ka rule** — agar requirement ambiguous hai, ticket finalize karne se pehle khud LLM ko instruct kiya jayega: "agar clarity nahi hai to guess mat karo, `clarification_needed` flag lagao"
- QA/merge karte waqt code-review reasoning — kya ye ticket scope se match karta hai, kya extra files touch hui

**Worker ka System Prompt** encode karega:
- Full-stack dev capability (jitni ticket ko chahiye)
- Git troubleshooting — conflict markers padhna, intent samajhna, safe resolve vs kab escalate karna hai
- Web reading/analysis skill — AI Studio ya kisi bhi UI ko samajhna, interact karna
- **Sabse important rule:** agar ticket ka scope clear nahi hai, ya koi decision leni hai jo ticket me define nahi — worker LLM ko explicitly instruct kiya jayega: *"assumption pe development mat karo — kaam pause karo, DB me `blocked_clarification` status daalo, sawaal likho, human/master ka jawab aane tak wait karo."* Isse ek **forced checkpoint** ban jaata hai.
- Self-review checklist code push karne se pehle: scope match, koi extra file touch nahi hui, tests pass

### 3.2 Prompt Engineering — Ticket Se Prompt Kaise Banega

Jab Master ek ticket create karta hai, wo sirf ek chhota text nahi hota — worker ko jo actual prompt milega wo **DB se context inject karke banaya jaata hai**:
- Ticket ka exact scope
- Project ki coding conventions/style guide (`config` collection se)
- Related pehle wale tickets/code patterns (agar dependency hai)
- Definition of done

Ye "prompt template" khud `config` collection me store hoga, taaki time ke saath improve/version kiya ja sake (`v1`, `v2`).

### 3.3 Clarification Protocol (Naya Ticket Status)

Ticket lifecycle:
```
open → claimed → in_progress → review → done
                      │
                      ▼ (agar LLM ko clarity nahi mili)
              blocked_clarification
                      │
                      ▼ (human ya master jawab de)
                  in_progress (resume)
```
Jab status `blocked_clarification` ho:
- DB me ek `question` field save hoga (LLM ne kya poocha)
- Telegram pe human ko turant tag/alert
- Jab tak jawab na aaye, wo worker doosra ticket claim kar sakta hai (idle nahi baithega), aur jawab aane pe wapas isi ticket pe return karega

### 3.4 Intelligence Layer — Actual Model Setup (Aapke Resources Ke Hisaab Se)

**Primary engine — Gemini Pro (1-year free access):** Har bot ka apna alag Gemini Pro access hoga. Ye system ka main "dimaag" rahega — Flash se kaafi behtar reasoning quality, isliye full-stack decisions aur coding dono ke liye reliable.

**Backup engine — OpenRouter free models:** Jab Gemini Pro kisi bot ke liye unavailable ho (quota hit, rate limit, ya temporary outage), wahi bot **automatically OpenRouter ke free-tier models** pe fallback karega (Llama 3.3, DeepSeek R1, Qwen variants).

**Ek exception — Ticket Generation:** Master ka **ticket-generation step Gemini Pro pe fixed/pinned** rahega, **koi fallback nahi**. Agar Gemini Pro us waqt unavailable hai, ticket generation **wait/queue** karega jab tak quota wapas na aaye — kabhi bhi silently weak model pe switch nahi hoga is specific kaam ke liye.

**Fallback logic (Model Router):**
```
Task aata hai (koi bhi prompt call)
        │
        ▼
   Kya ye "ticket_generation" type hai?
        │
   ┌────┴────┐
  Haan       Nahi
   │           │
   ▼           ▼
Sirf Gemini   Gemini Pro try karo
Pro try karo   │
(fail → wait,  ▼
retry later)  Fail? (quota/rate-limit/error)
               │
          ┌────┴────┐
         Haan       Nahi
          │           │
          ▼           ▼
   OpenRouter free   Result use karo
   model try karo
          │
     ┌────┴────┐
    Success    Fail bhi
      │           │
      ▼           ▼
  Result use   status = needs_human_review
   (audit_log   (dono backend fail — 
   me note:     agar guess karke aage
   "fallback    badha to risk zyada
   model use    hai bajaye pause karne ke)
   hua")
```

## 4. Bot Identity, Accounts & Free-Tier Resource Strategy

### 4.1 Har Bot Ka Identity Bundle

| Account | Kis liye | Kaise use hoga |
|---|---|---|
| **Git/GitHub account** (1 per bot) | Commit authorship, branch ownership | `git config user.name/email` us bot ke naam se; apna Personal Access Token (PAT) us account ka |
| **Google account (Gemini Pro)** | Primary Intelligence Layer — coding, reasoning, ticket generation | Har bot ka apna alag Gemini Pro access |
| **OpenRouter account (free models)** | Backup Intelligence Layer — jab Gemini Pro unavailable ho | Automatic fallback |
| **Manus AI account** | Task-execution / agent capability | Apna free tier alag se |
| **Replit account** | Compute / hosting execution environment | Cloud runtime |
| **Hugging Face account** | Free inference API / backup model hosting | 3rd fallback |

### 4.2 Git Setup
- Har bot us repo me collaborator apne unique GitHub account se
- Unique branch naming: `worker-1/ticket-104`, `worker-2/ticket-107`
- Local `.env` me PAT token (DB ya Telegram me kabhi nahi)

### 4.3 Free-Tier Quota Tracking
- `config` collection me har bot ka daily usage counter
- Quota khatam hone par `quota_exhausted` auto-flag aur load-balancing

## 5. Master Election (Race-Proof)

Atomic DB Compare-And-Swap (CAS) transaction guarantees exactly one winner:
- Heartbeat interval: 30-60 seconds (`last_heartbeat`)
- Timeout expiry: 2-3 minutes
- Monotonic `epoch` number increment on election
- Telegram announcement is strictly a notification, not a decision

---

## 6. Master Ka Role

1. **Priority decide karna** (`projects` collection)
2. **Tickets banana** (exact scope, file paths, APIs, `depends_on`)
3. **QA/Merge (Docker ke andar)**: Clean container spin up → dependencies install → tests run → container destroy. Pass = merge + save rollback commit hash. Fail = new hotfix ticket + attempt_count++.
4. **Dead ticket watchdog** (claimed 30+ min purana without progress -> back to `open`)
5. **Max attempt check** (attempt > 3 -> `needs_human_review`)
6. **Idle time me worker ban jaana** (open ticket pick karna, but preempted immediately if `review` ticket arrives)

---

## 7. Worker Ka Role

1. Read DB state
2. Announce idle
3. Atomic claim on open ticket (verify `depends_on == done`)
4. AI Studio availability check
5. Git pull backup branch
6. Code synthesis via context-injected prompt (zero assumptions, halt on ambiguity)
7. Local Docker container self-test
8. Progress audit logging
9. Git push to backup branch + ticket status = `review`

---

## 8. Telegram Group — Role & Commands

- Status announcements & alerts
- Human control commands: `/pause`, `/resume`, `/status`, `/hotfix <desc>`, `/force_master <id>`, `/stop_after_current`
- Tag isolation (`@sutradhar_update_bot`) to prevent crosstalk with other bots in multi-bot groups

---

## 9. Baaki Sab Gaps Solutions Matrix

| Gap | Solution |
|---|---|
| Race condition (master/ticket) | DB atomic CAS transactions |
| Split-brain | Heartbeat + periodic self-check + monotonic epoch |
| Dead ticket | `claimed_at` timestamp + watchdog |
| Infinite retry / cost blowup | `attempt_count` cap (3) → human escalation |
| Multi-project confusion | `project_id` scoping in every ticket |
| Context loss for new worker | DB is always current — just read it |
| Audit trail | `audit_log` collection + Git commit history (per-bot identity) |
| Environment drift | **Docker** — fixed Dockerfile/compose, same environment sab jagah |
| Security | Per-bot token, DB access via scoped service accounts, no hardcoded secrets |
| Telegram downtime | DB works independently — Telegram sirf notify karta hai, kaam nahi rukta agar Telegram down ho |
| Graceful shutdown | Worker `/stop_after_current` command sunta hai |
| AI Studio automation fail | Retry with backoff (max 3), fail hone pe ticket → `needs_human_review` |
| Git conflict fail | Auto-resolve try karo; fail → ticket → `needs_human_review`, human tag |
| LLM galat assumption/sawaal loop | `blocked_clarification` status — assume karne ki jagah pause + human se poochna |
| Bot identity/traceability | Har bot ka apna Git account + PAT token, unique commit author |
| Free-tier quota exhaustion | Per-bot usage counter, `quota_exhausted` self-flag, auto load-balance |

## 11. 12 Naye Operational Gaps (Blueprint v6.0)

| # | Gap | Solution |
|---|---|---|
| 1 | Bot process crash (script khud, ticket nahi) | Process supervisor (systemd/pm2/cron-watchdog) — bot script crash ho to auto-restart, restart hone pe DB se apna last state resume kare |
| 2 | DB single point of failure | DB provider ka managed high-availability tier use karo (Firestore/Supabase multi-region); local cache fallback — agar DB temporarily unreachable, bot apna current ticket pe kaam jaari rakhe, sirf naya claim na kare jab tak DB wapas na aaye |
| 3 | Ticket dependency enforcement | Ticket-claim query me filter: `status=open AND (depends_on is null OR depends_on.status=done)` — dependent ticket tab tak "claimable" hi nahi dikhega |
| 4 | Merge queue ordering | Master `review` tickets ko FIFO (`claimed_at`/`submitted_at` order) me process kare; agar priority flag hai to priority pehle, phir FIFO |
| 5 | Bad merge rollback | Har merge se pehle target branch ka commit hash `rollback_commit` me save; rollback = us commit pe `git revert`, naya `hotfix` ticket auto-generate |
| 6 | Docker test secrets | Secrets kabhi image me bake nahi hote — runtime pe `--env-file` (local `.env`, git-ignored) se container ko diye jaate hain; har bot ka apna local secrets file, kabhi DB/Telegram me nahi |
| 7 | Human response timeout | `blocked_clarification` ticket agar X ghante (jaise 4-6) tak unanswered rahe → Telegram reminder auto-resend; worker isi beech doosra ticket kaam kar sakta hai |
| 8 | Notification fatigue | Telegram pe sirf **state-change events** bhejo (claimed/done/failed/blocked), routine progress-logs sirf DB me jaayein; ek daily/hourly summary message optional |
| 9 | Prompt/template versioning | `config` collection me prompts version-tagged (`v1`, `v2`); naya version pehle 1 worker pe test karo, phir sabpe rollout — kabhi bhi bulk change directly production sab bots pe nahi |
| 10 | Max parallel workers | `system_state` me `max_concurrent_workers` cap; naya worker agar limit cross kare to "standby/idle" reh jaye jab tak slot free na ho |
| 11 | Test data/fixtures | Repo me hi ek `fixtures/` folder — seed/mock data maintain, Docker test isi pe chale (real production data kabhi bhi test me use nahi) |
| 12 | "Why" documentation | `audit_log` me har major decision ke saath ek `reasoning` field bhi save ho (LLM se hi ek-line reasoning generate karwao) — sirf "kya hua" nahi, "kyun hua" bhi trace ho sake |

## 12. Complete Core Pipeline — Step by Step With Troubleshooting

### A. Bot Startup & Supervision
- Process supervisor starts script. Reads identity from local `.env`. Resumes last known state from DB.
- **Troubleshoot:** If restarting in loop, inspect credentials and local cache sync.

### B. Master Election
- Atomic CAS transaction on `current_master`.
- **Troubleshoot:** If two bots announce master on Telegram, check DB `current_master` — DB is truth.

### C. Master: Project Intake & Ticket Generation
- Gemini Pro pinned (Zero fallback).
- **Troubleshoot:** If Gemini Pro quota exhausted, ticket generation queues and waits; does not downgrade to weak model.

### D. Worker: Ticket Discovery & Claim
- Query `status=open` AND `depends_on == done`. Atomic CAS claim.
- **Troubleshoot:** If no claimable ticket, wait until upstream finishes.

### E. Worker: Environment/AI Studio Availability Check
- Retry with backoff (max 3); escalate to `needs_human_review` if persistent fail.

### F. Worker: Git Pull (Backup Branch)
- Pull dedicated backup branch (`worker-N/ticket-XXX`).

### G. Worker: Development (Intelligence Layer Execution)
- Context-injected prompt. Gemini Pro -> OpenRouter fallback. If ambiguous -> `blocked_clarification`.

### H. Worker: Local Docker Self-Test
- Run tests in container using `fixtures/` dataset.

### I. Worker: Git Push + Ticket → Review
- Push backup branch and set status to `review`.

### J. Master: QA (Docker) + Merge/Reject
- FIFO/Priority merge queue in clean Docker container. If pass, save `rollback_commit` and set `done`.

### K. Watchdog: Dead Ticket Recovery
- Re-open tickets unclaimed or stalled > 30 minutes without logs.

### L. Clarification Flow
- Block, ask question, notify human. Unblock upon answer.

### M. Kill Switch / Emergency Pause
- `/pause` sets `global_status: PAUSED` in DB. All workers halt safely at checkpoint.
